### !!sections intro

If you are building a web server in Rust and need to manage a little bit of shared state, you will likely use a Mutex. Mutexes can be hazardous, leading to weird and difficult to debug errors, and the Rust ecosystem often lets you avoid dealing with them yourself (for example a lot of rust client libraries use mutexes internally, so you don't have to), but if you need to manage some shared state inside a server yourself, they are often the simplest and most straightforward way to do so. Before you even get to using a mutex though, you run into a problem. There are two main mutex's to choose from, [std::sync::Mutex](https://doc.rust-lang.org/std/sync/struct.Mutex.html) and [tokio::sync::Mutex](https://docs.rs/tokio/latest/tokio/sync/struct.Mutex.html), and it is not immediately obvious which one you should use.

`std::sync::Mutex` is a regular mutex. You acquire a lock on the mutex by calling `lock()`, which blocks the thread until the lock is acquired. `tokio::sync::Mutex` on the otherhand is an async mutex. Instead of blocking the thread, `lock()` returns a future that you await, handing the thread back to Tokio until the lock is acquired. Since the thread is handed back to the Tokio runtime while you wait for the lock, you can safely hold a lock on a tokio mutex over an await. Attempting to hold a std mutex over an await usually results in a compiler error. For example

```rust
// a placeholder async function
async fn do_async_stuff() {}

// creates and holds a Tokio mutex over an await
async fn succeeds() {

  let tokio_mutex = tokio::sync::Mutex::new(1usize);
  {
    let _mutex_guard = tokio_mutex.lock().await;
    do_async_stuff().await;
    // `_mutex_guard` is dropped here releasing the mutex
  }
}

// creates and holds a std mutex over an await
async fn fails() {
  let std_mutex = std::sync::Mutex::new(1usize);
  {
    let _mutex_guard = std_mutex.lock().unwrap();
    do_async_stuff().await;
    // `_mutex_guard` is dropped here releasing the mutex.
  }
}

#[tokio::main]
async fn main() {
  tokio::spawn(async move { succeeds().await });
  tokio::spawn(async move { fails().await }); 
}
```

The only difference between `succeeds` and `fails` is that `fails` uses a std mutex but the line `tokio::spawn(async move { fails().await });` throws a compiler error. We'll get to why the error occurs on that line a little later. There are some situations where holding a std mutex over an await doesn't throw an error, but even then it's a bad idea. Since the std mutex blocks a thread while waiting for the lock, all of the executor's threads can end up being blocked without a way for the original lock to be released, quickly deadlocking the tokio runtime.

```rust
use std::sync::{Arc, Mutex};

async fn lock_and_sleep(data: Arc<Mutex<()>>) {

  let future_a = lock_and_sleep(data.clone());
  let future_b = lock_and_sleep(data.clone());

  // future_a acquires the lock and yields the thread
  // future_b then blocks the thread attempting to acquire the lock
  // future_a is has no thread to release the lock with
  tokio::join!(future_a, future_b);

  println!("Never reached!") 
}
```

This example uses a single threaded tokio runtime. future_a executes first, acquiring the lock and then yielding the thread. future_b then blocks the thread attempting to acquire the lock. future_a then can never release the lock because the only executor thread is occupied.

Since you’re working in Tokio’s async context, you’d think you should just use Tokio's mutex that is compatible with awaits, but the recommendation is actually to default to the std mutex and only switch to Tokio’s mutex if needed.

The immediately explanation for this choice is often performance. Tokio's mutex uses a std mutex under the hood in addition to doing a few other operations to make it work in the async context, so it is never going to be faster than the std mutex. Since most mutex use cases don't require holding a lock over an await, or holding a lock long enough to cause issues with the tokio runtime, the conventional wisdom is to just use the option that is more performant. 

However, I would argue that performance is not a good reason to choose `std::sync::Mutex` over `tokio::sync::Mutex`. Let’s make a quick benchmark.

```rust
#[tokio::main]
async fn main() {
  let n = 10000;

  // Lock and release a std mutex a bunch of times
  // and print the average lock time
  let std_mutex = std::sync::Mutex::new(0u64);
  let start = Instant::now();
  for _ in 0..n {
    std_mutex.lock().unwrap();
  }
  let duration = start.elapsed();
  println!("average time to lock std mutex: {}ns", 
    duration.as_nanos() / n);
  
  // Lock and release a Tokio mutex a bunch of times
  // and print the average lock time
  let tokio_mutex = tokio::sync::Mutex::new(0u64);
  let start = Instant::now();
  for _ in 0..n {
    tokio_mutex.lock().await;
  }
  let duration = start.elapsed();
  println!("average time to lock tokio mutex: {}ns", 
    duration.as_nanos() / n);
}
```

Running this on my laptop, I got the following results.

```
average time to lock std mutex: 3ns
average time to lock tokio mutex: 18ns
```

This gives a decent idea of how fast each mutex is. The std mutex is in fact significantly faster than Tokio's mutex in absolute terms, about 6 times faster, but here’s the thing. It. Doesn’t. Matter.

Even though the std mutex is faster, the Tokio mutex still only averaged about 18 nanoseconds to lock. An operation that takes 18 nanoseconds can be measured in 10s of cpu cycles. Unless you're working for a low latency trading firm or locking lots of mutexes in a tight inner loop, your choice of mutex is not going to affect the performance of your web server's endpoint handler. 

So what gives? The Rust community tends to be very no cost abstraction oriented, but surely they wouldn’t be telling the average web developer to use a mutex that is less good just for a performance improvement that has no significance for their use case. I would argue there is a much more compelling reason than performance for the developer of a webserver to prefer using the std mutex by default. Here is an only somewhat contrived example using a mutex in a web server. 

Let's say we have a webserver that needs to get data from a lot of Postgres databases. Like, a lot a lot. We also want to be able to add new databases on the fly without restarting the server. We can make a [sqlx](https://docs.rs/sqlx/latest/sqlx/index.html) Postgres client for each database we connect to. Like most Rust client tools, the sqlx client uses [Arcs](https://doc.rust-lang.org/std/sync/struct.Arc.html) and mutexes internally that allow you to just pass around a clonable reference to it, but since we need a lot of these clients and we need to add more while the server is running, we'll store them in a map with an id for each one and wrap that map in a mutex<FootnoteRef id="fnref-2" href="#fn-2">2</FootnoteRef>. We'll add a single endpoint that gets data from a database of choice and ignore the endpoint that creates new clients for now.


```rust
use std::{collections::HashMap, net::SocketAddr, sync::Arc};
use axum::{Router, extract::{Path, State}, http::StatusCode,
           routing::get};
use sqlx::PgPool;
use tokio::sync::Mutex;
use uuid::Uuid;

// Shared server state that wraps a client map in a mutex
#[derive(Clone, Default)]
struct AppState {
  client_map: Arc<Mutex<HashMap<Uuid, PgPool>>>,
}

// Create and run the server
#[tokio::main]
async fn main() {
  let state = AppState::default();
  let app = Router::new()
    .route("version/{id}", get(get_from_db))
    .with_state(state);
  let addr = SocketAddr::from(([127, 0, 0, 1], 3000));

  axum_server::bind(addr).serve(app.into_make_service())
    .await.unwrap();
}

// Handle requests for data
async fn get_from_db(
    State(state): State<AppState>,
    Path(id): Path<Uuid>,
) -> Result<String, StatusCode> {
  // Lock the map and get the request database's client
  let map_guard = state.client_map.lock().await;
  let client = map_guard.get(&id)
    .ok_or(StatusCode::NOT_FOUND)?;

  // Get data from the requested database with a 
  // placeholder query
  sqlx::query_scalar::<_, String>("SELECT version()")
    .fetch_one(client).await
    .map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)
}
```

The `get_from_db` endpoint handler is pretty simple here. It locks the map of clients, gets the client for the database we need, and sends a query to it. But there's a problem. In my haste to implement this critical endpoint, I failed to notice that the lock for our `client_map` is not released until the end of the function, after we have completed a query to the database! This kills our server's concurrency, only allowing one network request to any database at a time. Locking the mutex may be fast, but we have now bottlenecked our server on a proportionately slow network request. Even within a single zone, network requests run on a scale of milliseconds (1,000,000 nanoseconds). Forcing all of our database queries to run one after the other will dramatically degrade our server's performance.

And here’s the thing, this is hard to detect. From a correctness stand point, there's nothing wrong with this code. The right data is being returned from the right databases, so basic correctness tests will pass. We won't see high cpu usage, because the cpu isn't being used. todo: do a quick test to confirm cpu utlization doesn't shoot up in this case. All requests are just awaiting the mutex. In this particularly flagrant case, we'd probably notice the issue when this endpoint starts timing out under high request load, or if our engineers are really on top of their observability, we might notice that the response time for the endpoint is unusually high, but on a less frequently used path, this could go undetected causing low grade performance degradation and sporadic seemingly unrelated errors for a long time.

Which gets to the main point of this article. Holding a mutex over an await is usually a really bad idea, and a mutex that allows you to do that is often times an anti-feature. If we replace the Tokio mutex with a std mutex in the code above, we receive a compiler error 
```
the trait bound 'fn(State<AppState>, 
axum::extract::Path<Uuid>) -> impl std::future::Future<Output
= Result<std::string::String, StatusCode>> {get_from_db}: 
Handler<_, _>' is not satisfied
```

This is... not the most helpful error unfortunately, but it is better than nothing. We can fix the error by releasing the lock before the database query is made.

```rust
async fn get_from_db(
    State(state): State<AppState>,
    Path(id): Path<Uuid>,
) -> Result<String, StatusCode> {
  // Lock the map, clone the client, and release the lock
  let client = {
    let map_guard = state.pools.lock().unwrap();
    map_guard.get(&id)
      .ok_or(StatusCode::NOT_FOUND)?.clone()
  };

  // Send a placeholder query retrieving the 
  // databases version
  sqlx::query_scalar::<_, String>("SELECT version()")
    .fetch_one(&client).await
    .map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)
}
```

Now we only briefly lock the mutex to retrieve the cheaply cloneable client and release the lock immediately after, removing the bottleneck.

This error is a bit more helpful than the axum error (and the compiler also gives some helpful notes that help pin point the problem). It is not immediately obvious what is happening, but we can see that the spawn function is expecting a function returning .
The immediate problem is that the spawn function takes an async function that returns a future that is `Send`. 

The immediate answer is that holding a std mutex guard over an await makes the function's future `!Send`, but that is kind of like saying grass is green because it is filled with green stuff (todo: link xkcd). To understand what is happening, we need to look into two rust concepts a bit deeper, Send and futures.

The `Send` trait indicates that a value can be safely moved between threads, and if the value is not `!Send`, "not Send", it cannot be. This trait is automatically implemented for structs and enums that are composed of `Send` values, but introducing one `!Send` value into a struct forces that entire struct to be !Send. 

In Rust, async functions desugar to regular functions that return a `Future`. This future is a state machine that holds everything needed to execute the async function's code between awaits. The future gets passed aroudn with executor threads running each synchronous block of code in the future. When you create a value in the function and have not dropped it before reaching an await, that value needs to be stored in the future so that the state is available when execution is picked back up after the await.

The mutex guard you receive when you lock a std mutex is !Send, and when you hold a std mutex guard over an await that mutex guard has to be stored in the future. This then makes the entire `!Send`

As far as the compiler is concerned there is nothing inherently wrong with haveing a !Send future, and you can sometimes get away with it. (example code from earlier) But task spawn creates a situation where a future may be moved between threads, so it requires the future to be Send. Simlarly axum handlers are required to be send, presumably because they are spawned on a task, so if you are using axum, you will pretty much always get an error holding a std mutex lock over an await.

So the std mutex guard kind of drunkenly stumbles into giving us a compiler error when we want it often, but not all of the time and frequently with a somewhat confusing error message.

It would be great if the compiler would consider holding a std mutex lock over an await an error, and always flag it at the site it occurs. There is actually a compiler check that is applied to std mutex guards, `must_not_suspend`, that you can enable, but this check is only available on nightly. If you are using nightly, you can enable the check by adding  

```
#![feature(must_not_suspend)]
#![deny(must_not_suspend)]
```
to your project root (eg. src/main.rs or src/lib.rs).

If you are on the stable channel, you can check for this with Clippy, Rust's linter. By default, Clippy will give a warning when a std mutex is held over an await. You can upgrade that to an error by adding

But if you should use the std mutex for most use cases, when should you use the Tokio mutex? One example is request coallescing. I wrote a webhook auth library recently (it's called [Correct Hooks](https://github.com/handlewithcarecollective/correct-hooks), it's awesome and you should check it out). One part of the library is responsible for retrieving and refreshing key sets from a known endpoint. The events that trigger this refresh can and likely will happen repeatedly in a short burst. If a refresh request is already in progress when another refresh is triggered, the library shouldn't send another http request. The results of the refresh that is already in progress are sufficient, and we would like the secondary refresh to use those results as its own. This is a great time to use an async mutex. Here is a slimmed down example.

```rust
use std::sync::Arc;
use serde_json::json;
use uuid::Uuid;

struct KeySet {
  key_set_json: serde_json::Value,
  refresh_id: Uuid,
}

pub struct Verifier {
  key_set: Arc<std::sync::RwLock<KeySet>>,
  refresh_lock: Arc<tokio::sync::Mutex<()>>,
}

impl Verifier {
  async fn refresh_jwks(&self) -> Result<(), String> {
    // get the old refresh id
    let old_id = { self.key_set.read().unwrap().refresh_id };
    
    // acquire the tokio refresh lock
    let _refresh_lock = self.refresh_lock.lock().await;
    
    // if the refresh id has changed, the key set has already been updated. Return early.
    let current_id = { self.key_set.read().unwrap().refresh_id };
    if current_id != old_id {
      return Ok(());
    }

    // fetch the new key set
    let new_key_set_json = self.fetch_key_set().await;

    // set the new key set and refresh id values
    *self.key_set.write().unwrap() = KeySet {
      key_set_json: new_key_set_json,
      refresh_id: Uuid::new_v4(),
    };

    Ok(())
  }

  // mock function fetching the key set from an endpoint
  async fn fetch_key_set(&self) -> serde_json::Value {
    json!({})
  }
}
```

Here we use two locks, one [std::sync::RwLock](https://doc.rust-lang.org/std/sync/struct.RwLock.html) and one Tokio Mutex. We briefly lock the RwLock to access or set values on the key set, and use the Tokio mutex to regulate request flow.

When the refresh function is called, we first get the current `refresh_id` and then acquire a lock on the Tokio mutex. If there is no existing refresh in progress, the lock is acquired, the new key set is retrieved, and the refresh id is updated. If there is a refresh in progress, when the lock is eventually acquired, the changed refresh id is detected and the function returns early since the key set was already updated. The Tokio mutex is not only preferred, but necessary here. We **want** to only one network request to be sent at a time, and the Tokio mutex lets us do that. 

Since holding a mutex lock over an await boundary causes difficult to diagnose problems in most use cases, the std mutex preventing that makes it a preferable default over the Tokio mutex. In the end the reason for defaulting to `std::sync::Mutex`  kind of about performance, but it's more about the Rust ecosystem trying (again) to stop you from shooting yourself in the foot. And when you need to switch to the Tokio mutex it immediately apparent.
