Rust Tokio Mutex vs Std Mutex: It's not about performance

by Phillip Diffley

If you build a web server in Rust and need to manage a little bit of shared state you will likely use a Mutex. But you quickly run into a problem. There are two Mutex's to choose from, std::sync::Mutex and tokio::sync::Mutex.

std::sync::Mutex is a regular mutex. You attempt to acquire the lock, and the thread blocks until the lock is acquired. tokio::sync::Mutex is an async mutex. You await the call to lock instead of blocking the thread. Instead of blocking the thread when you call lock(), you await the result, handing the thread back to Tokio until the lock in acquired. You can also hold tokio::sync::Mutex over an await1. If you try to do that with a std::sync::Mutex you get a compile time error.

#[tokio::main]
async fn main() {
  tokio::spawn(async move { succeeds().await });
  // This line returns an error
  tokio::spawn(async move { fails().await }); 
}

async fn succeeds() {
  let tokio_mutex = tokio::sync::Mutex::new(1usize);
  {
    let _guard = tokio_mutex.lock().await;
    do_async_stuff().await;
  }
}

async fn fails() {
  let std_mutex = std::sync::Mutex::new(1usize);
  {
    let _guard = std_mutex.lock().unwrap();
    do_async_stuff().await;
  }
}

async fn do_async_stuff() {}

Since you’re working in Tokio’s async context, so you’d think you should just use the async mutex, but the recommendation is actually to default to std mutex and only switch to Tokio’s mutex if needed.

The immediately explanation for this choice is often performance. Tokio's mutex uses a std mutex under the hood in addition to doing a few other operations to make it work in the async context, so it is never going to be faster than the std mutex. The std mutex blocks a thread, which is usually a bad idea within an async context, but for the most common use cases, you won't block long enough to cause a problem. The conventional wisdom is to just use the option that is more performant.

However, I would argue that performance is not a good reason to choose std::sync::Mutex over tokio::sync::Mutex. Let’s make a quick benchmark.

#[tokio::main]
async fn main() {
  let n = 10000;

  let std_mutex = std::sync::Mutex::new(0u64);
  let start = Instant::now();
  for _ in 0..n {
    std_mutex.lock().unwrap();
  }
  let duration = start.elapsed();
  println!("average time to lock std mutex: {}ns", 
    duration.as_nanos() / n);
  
  let tokio_mutex = tokio::sync::Mutex::new(0u64);
  let start = Instant::now();
  for _ in 0..n {
    tokio_mutex.lock().await;
  }
  let duration = start.elapsed();
  println!("average time to lock tokio mutex: {}ns", 
    duration.as_nanos() / n);
}

Running this on my laptop, I got the following results.

average time to lock std mutex: 3ns
average time to lock tokio mutex: 18ns

This gives a decent idea of how fast each mutex is. The std mutex is in fact significantly faster than Tokio's mutex in absolute terms, about 6 times faster but here’s the thing. It. Doesn’t. Matter.

Even though the std mutex is faster, the Tokio mutex averaged about 18 nanoseconds to unlock. An operation that takes 18 nanoseconds can be measured in 10s of cpu cycles. Unless you're working for a low latency trading firm or locking lots of mutexes in a tight inner loop, your choice of mutex is not going to affect the performance of your web server's endpoint handler.

So what gives? The rust community tends to be very no cost abstraction oriented, but surely they wouldn’t be telling the average web developer to use a mutex that is less good just for a performance improvement that has no significance for their use case. I would argue there is a much more compelling reason than performance for the developer of a webserver to prefer using the std mutex by default.

Here is an only somewhat contrived example using a mutex in a web server. Let's say we have a webserver that needs to get data from a lot of Postgres databases. Like, a lot a lot. We also want to be able to add new databases on the fly without restarting the server. We can make a sqlx Postgres client for each database we connect to. Like most rust client tools, the sqlx client uses Arcs and mutexes internally that allow you to just pass around a clonable reference, but since we needed a lot of these clients, we'll store them in a map with an id for each one. So that we can add to the map of clients while the server is running, we wrap the map in a mutex2. We'll add a single endpoint that gets data from a database of choice and ignore the endpoint that creates new clients for now.

use std::{collections::HashMap, net::SocketAddr, sync::Arc};
use axum::{Router, extract::{Path, State}, http::StatusCode,
           routing::get};
use sqlx::PgPool;
use tokio::sync::Mutex;
use uuid::Uuid;

// Shared server state that wraps a client map in a mutex
#[derive(Clone, Default)]
struct AppState {
  client_map: Arc<Mutex<HashMap<Uuid, PgPool>>>,
}

// Create and run the server
#[tokio::main]
async fn main() {
  let state = AppState::default();
  let app = Router::new()
    .route("version/{id}", get(get_from_db))
    .with_state(state);
  let addr = SocketAddr::from(([127, 0, 0, 1], 3000));

  axum_server::bind(addr).serve(app.into_make_service())
    .await.unwrap();
}

// Handle requests for data
async fn get_from_db(
    State(state): State<AppState>,
    Path(id): Path<Uuid>,
) -> Result<String, StatusCode> {
  // Lock the map
  let map_guard = state.client_map.lock().await;
  let client = map_guard.get(&id)
    .ok_or(StatusCode::NOT_FOUND)?;

  // Placeholder query retrieving the databases version
  sqlx::query_scalar::<_, String>("SELECT version()")
    .fetch_one(client).await
    .map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)
}

The get_from_db endpoint handler is pretty simple here. It locks the map of clients, gets the client for the database we need, and sends a query to it. But there's a problem. In my haste to implement this critical endpoint, I failed to notice that the lock for our client_map is not released until the end of the function after we have completed our query to the database! This kills our server's concurrency, only allowing one network request to any database at a time. Locking the mutex may be fast, but we have now bottlenecked our server on a proportionately slow network request.

And here’s the thing, this is hard to detect. From a correctness stand point, there's nothing wrong with this code. Basic correctness tests will pass. We won't see high cpu usage, because the cpu isn't being used. All requests are just waiting on the mutex. In this particularly flagrant case, we'd probably notice the issue when this endpoint starts timing out under high request load, or if our engineers are really on top of their observability we might notice that the response time for the endpoint is high beforehand, but if the code that incorrectly locks access to the database clients was on a less frequent path, the errors would likely be sporadic and be triggered by higher throughput paths that lead us away from the source of the problem.

Which gets to the main point of this article. Holding a mutex over an await is usually a really bad idea, and allowing you to do that is often times an anti-feature. If we replace the Tokio mutex with a std mutex in the code above, we receive a compiler error

the trait bound 'fn(State<AppState>, 
axum::extract::Path<Uuid>) -> impl std::future::Future<Output
= Result<std::string::String, StatusCode>> {get_from_db}: 
Handler<_, _>' is not satisfied

This is... not the most helpful error unfortunately, but it is better than nothing. We can fix the error by releasing the lock before the database query is made.

async fn get_from_db(
    State(state): State<AppState>,
    Path(id): Path<Uuid>,
) -> Result<String, StatusCode> {
  // Lock the map
  let client = {
    let map_guard = state.pools.lock().unwrap();
    map_guard.get(&id)
      .ok_or(StatusCode::NOT_FOUND)?.clone()
  };

  // Send a placeholder query retrieving the 
  // databases version
  sqlx::query_scalar::<_, String>("SELECT version()")
    .fetch_one(&client).await
    .map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)
}

But if the Tokio mutex is prone to misuse, when should you use it? One example is request coallescing. I wrote a webhook auth library recently (it's called Correct Hooks, it's awesome and you should check it out). One part of the library is responsible for retrieving and refreshing key sets from a known endpoint. The events that trigger this refresh can and likely will happen repeatedly in a short burst. If a refresh request is already in progress when another refresh is triggered, the library shouldn't send another http request. The results of the refresh that is already in progress are sufficient, and we would like the secondary refresh to use those results as its own. This is a great time to use an async mutex. Here is a slimmed down example.

use std::sync::Arc;
use serde_json::json;
use uuid::Uuid;

struct KeySet {
  key_set_json: serde_json::Value,
  refresh_id: Uuid,
}

pub struct Verifier {
  key_set: Arc<std::sync::RwLock<KeySet>>,
  refresh_lock: Arc<tokio::sync::Mutex<()>>,
}

impl Verifier {
  async fn refresh_jwks(&self) -> Result<(), String> {
    // get the old refresh id
    let old_id = { self.key_set.read().unwrap().refresh_id };
    
    // acquire the tokio refresh lock
    let _refresh_lock = self.refresh_lock.lock().await;
    
    // if the refresh id has changed, the key set has already been updated. Return early.
    let current_id = { self.key_set.read().unwrap().refresh_id };
    if current_id != old_id {
      return Ok(());
    }

    // fetch the new key set
    let new_key_set_json = self.fetch_key_set().await;

    // set the new key set and refresh id values
    *self.key_set.write().unwrap() = KeySet {
      key_set_json: new_key_set_json,
      refresh_id: Uuid::new_v4(),
    };

    Ok(())
  }

  // mock function fetching the key set from an endpoint
  async fn fetch_key_set(&self) -> serde_json::Value {
    json!({})
  }
}

Here we use two locks, one std::sync::RwLock and one Tokio Mutex. We briefly lock the RwLock to access or set values on the key set, and use the Tokio mutex to regulate request flow.

When the refresh function is called, we first get the current refresh_id and then acquire a lock on the Tokio mutex. If there is no existing refresh in progress, the lock is acquired, the new key set is retrieved, and the refresh id is updated. If there is a refresh in progress, when the lock is eventually acquired, the new refresh id is detected and the function returns early since the key set was already updated. The Tokio mutex is not only preferred, but necessary here. We want to only one network request to be sent at a time, and the Tokio mutex lets us do that.

Since in most use cases, holding a mutex lock over an await boundary leads to significant performance degradation, the std mutex failing to compile in that case makes it preferable default over the Tokio mutex. When you need to switch to the Tokio mutex it is immediately apparent. In the end the reason for defaulting to std::sync::Mutex kind of about performance, but it's more about the rust ecosystem trying (again) to stop you from shooting yourself in the foot.

1 Specifically, it makes the returned future !Send, so the containing function cannot be spawned on a tokio::task. Any Axum handler needs to be Send though. We will see this come up later. 2 An RwLock would actually make more sense here, but we're just doing this for explanatory purposes.
